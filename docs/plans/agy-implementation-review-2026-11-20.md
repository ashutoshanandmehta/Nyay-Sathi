## Required corrections before deployment

### 1. Gmail and Drive report provider success without performing the operation

**Release blocker.** In `supabase/functions/nyay-api/handler.ts:3299`, the Gmail send handler creates a message ID from the payload hash, writes `dispatchStatus: 'sent_confirmed'`, updates approval to dispatched, and returns `sent: true`. This path does not send an email through Gmail. The success notice explicitly says the email was sent.

The reconciliation handler at `handler.ts:3336` accepts the client's `provider_sent_found` boolean and message IDs, then can record `reconciled_sent` without independently checking Gmail.

Drive has the same issue. Folder creation at `handler.ts:2841` generates or accepts an ID locally. Upload at `handler.ts:2929` generates or accepts a file ID, writes `syncStatus: 'synced'` and `originalPreserved: true`, and constructs a Google Drive URL without uploading the original file.

The token connection path also accepts client-provided account identity and scopes. Storing encrypted tokens and checking claimed scope strings does not establish that a verified Google account granted those scopes.

**Required work:** implement real provider adapters and secure account authorization/token verification, refresh and revocation. Derive account identity, granted scopes, file IDs, message IDs, and reconciliation results from verified provider responses. Keep simulation behavior in test doubles. If an adapter is absent, return an explicit unavailable result without writing success. Add an atomic dispatch reservation so concurrent sends cannot reuse an approval; reconcile ambiguous sends through provider evidence before retrying. Credential availability is necessary but will not repair the current handlers by itself.

**Acceptance:** faithful HTTP fixtures prove the provider requests and failure handling; a separately authorized live smoke test demonstrates an uploaded original, a sent email, and reconciliation against actual provider records. Provider failure, missing adapter, forged identity/scope claims, client-supplied success, and concurrent requests must never create false success.

### 2. The real AI adapter loses standard raw Responses API output

**Release blocker.** `supabase/functions/nyay-api/openai-provider.ts:336`, `:389`, and `:444` use `JSON.parse(data.output_text || '{}')` after raw `fetch` calls. Standard raw response text is in message content under `output`; `output_text` is an SDK convenience property. See the [official text generation documentation](https://developers.openai.com/api/docs/guides/text).

An offline fixture returned a completed response with:

```json
{"output":[{"type":"message","role":"assistant","content":[{"type":"output_text","text":"{\"central_question\":\"Question\",\"tasks\":[],\"claims\":[]}"}]}],"status":"completed"}
```

The actual adapter returned `{"kind":"answer","answer":{}}`. The existing transport test provides a top-level `output_text`, masking this defect. TypeScript casts do not validate received JSON.

**Required work:** parse actual message content or use an SDK with the documented helper; runtime-validate primary answers, reviews, repair outputs, and tool arguments. Handle refusal, missing content, incomplete responses, malformed output, tool continuations, and provider failures consistently. Reject empty/invalid results rather than treating `{}` as a valid answer or review.

**Acceptance:** tests for all three adapter methods use faithful raw HTTP fixtures, including refusals and incomplete responses. Keep paid evaluation separate from these offline transport checks.

### 3. Hindi PDF export is unreadable; long documents lose content

**Release blocker for document export.** `supabase/functions/nyay-api/documents.ts:576` constructs a single-page PDF using Helvetica, without Devanagari font embedding or shaping. The generated Hindi complaint rendered as garbled characters. Merely accepting UTF-8 input and returning PDF-signature bytes does not establish Hindi export support.

The same function silently cuts to 120 lines and 110 characters per line, then writes every retained line on one page with fixed line spacing. A 100-line English export had only one page and lost the final lines from page extraction/renderable content.

**Required work:** use a suitable PDF rendering library, supported embedded fonts and Hindi shaping, wrapping, and pagination. Do not silently discard complaint content. Add rendered Hindi and multi-page QA, with checks that beginning, middle, and final content survives. Do not restore the older worktree's exporter while integrating changes.

### 4. The claimed 50-page extraction limit does not select the first 50 pages

`documents.ts:175` counts page-like tokens and calculates an `extractedPages` label, but `:185` scans text operators throughout the raw document. Stream-count and literal-count limits are not page selection.

Reproduction using a valid, uncompressed 120-page PDF created by PyMuPDF, one unique marker per page:

```json
{"pages":120,"reportedExtractedPages":50,"includesPage120":true,"limitations":"Extracted first 50 of 120 pages within runtime bounds"}
```

**Required work:** parse the PDF page tree and only extract selected pages with accurate provenance. Handle ordinary compressed PDFs, font encodings, text order, scanned pages, and malformed inputs through supported parsing and explicit limitations. Test valid representative files instead of relying on synthetic text-operator fixtures.

**Acceptance:** a first-50-pages extraction excludes page 51 onward, preserves order and attribution, and reports accurate extraction status. Bound decompression, input sizes, and parser work independently of page-count metadata.

## Scope and performance claims that need qualification

- **Runtime feasibility:** Node `process.cpuUsage()`/heap measurements on synthetic workloads are useful local measurements, not proof of hosted Edge CPU/memory compliance. Run the corrected parser/exporter and representative workloads under the actual Supabase runtime, with concurrency, large inputs, decompression, cancellations and failure paths. Report measured conditions and limits.
- **Streaming:** `handler.ts:1043` emits answer blocks after complete review/coherence checks. Status and safety events can improve responsiveness, but the main answer still waits for primary generation and review/repair. This does not establish a faster time to first substantive answer. Measure time to first status, first safety message, first approved answer block, and completion separately. Preserve verification quality while reducing unnecessary serial work; do not publish unreviewed legal claims to improve a latency number.
- **Research:** `openai-provider.ts:451` routes research to the local proposition pack. It does not implement fresh external official-source research. Report local retrieval accurately and separately verify corpus coverage, temporal applicability, provenance, editorial approvals, and migration from the existing backend. Golden scenarios alone do not establish legal quality parity.
- **Android:** Java bridges and browser mocks are implementation evidence, not device verification. APK compilation, secure-storage behavior, cold-start deep links, back navigation, file sharing, token refresh, process death, and interrupted streams still require device checks.
- **Schema:** local PGlite tests are valuable, but do not establish successful hosted migration or an actual Supabase advisor run. Reconcile manually applied foundation migration history carefully before applying later migrations. Record hosted receipts separately from local assertions.
