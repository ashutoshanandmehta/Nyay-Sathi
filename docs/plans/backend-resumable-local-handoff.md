## Operational limits

The old fixed USD 4.95 reservation has been replaced by model-aware admission and terminal settlement. The Sol/Medium/4,096-token configuration reserves USD 1.328640 for at most six submissions, using a 64,000-byte serialized request bound, a conservative input-token/framing allowance, Standard rates and a 30-minute cache-write allowance. Each application input is separately capped at 48 KB. The output cap includes reasoning as well as visible output; tune it only after evaluation. This is an upper estimate for tracked model work, not an actual charge or a guarantee of answer quality.

Provider usage is recorded per intent/response, including input, cached input, cache writes by lifetime, output and reasoning token counts. Reasoning is a subset of output and is not charged twice. Completed, failed or cancelled runs settle against observed token usage at a stored price snapshot, releasing unused budget. A submitted call with missing usage or an uncertain receipt retains its per-call reserve; verified late receipts can reduce that hold exactly once. If cache-write details are absent, the cost calculation conservatively applies the 30-minute write rate to unclassified non-cached input until a fuller receipt is available. Invalid or conflicting receipts are rejected. Budget amounts use nine-decimal precision rather than rounding every call to four decimals.

The existing USD 5 project/day cap and owner caps remain. Several completed questions can therefore run in a day if their settled usage fits the cap; there is no promised question count. Active runs retain their full reservation until terminal settlement, so concurrent admissions are also bounded. Accounting uses the original admission day. Cost figures are application estimates based on usage and the recorded Standard rate card, not provider invoices; provider price changes, other tools/services, or requests outside this path need separate accounting and monitoring. No live cost or answer-quality evaluation was run. [Model prices](https://developers.openai.com/api/docs/models/gpt-6.2-sol) · [Cache pricing and usage fields](https://developers.openai.com/api/docs/guides/prompt-caching)

The pilot requires a dedicated managed provider key. Existing client-unlocked BYOK credentials require a separate durable authorization model because the worker cannot depend on the client staying connected. Do not migrate browser unlock secrets or persist them as job input.

## Agent observability

The new service-only tables are `nyay_runtime_runs`, `nyay_runtime_calls` and `nyay_runtime_steps`. RLS and grants deny direct access to anonymous/authenticated clients. They record model configuration, price version, reservations/settlement, token counters, stage attempts, active wall time, evidence/blocked-claim counts and outcomes. Run duration includes queue/wait time; step duration measures active wall time, not CPU. Observed model duration includes collection delay rather than claiming pure inference time. Normal pending polls are labeled `waiting`; error retries are distinct.

Inspect run-specific diagnostics through the authenticated owner-scoped route:

```text
GET /api/conversations/{conversation_id}/turns/{request_id}/metrics
```

The Edge layer verifies the customer session, and the service-only SQL query also checks owner/conversation/request ownership. Another customer receives no run diagnostics. This endpoint adds no new public product screen. Operators can run the read-only queries in `supabase/operations/agent-observability.sql` using an authorized database role, or filter function logs by the structured event type `nyay.agent.step`. Failed telemetry storage emits a content-free `nyay.agent.telemetry_unavailable` event without breaking publication; usage accounting itself remains mandatory and retains reserves on uncertainty.

Diagnostic rows/log events do not contain prompts, case text, extracted documents, email bodies, API tokens, opaque reasoning content or raw provider errors. Existing private workflow checkpoints still contain the case/model context needed for execution and retain their separate protection/retention obligations. Runtime diagnostic tables cascade with their owning execution; define production operational/financial retention before collecting real customer data. No third-party observability account, paid service, live dashboard or hosted configuration was created.

OpenAI temporarily stores background data even with `store:false` under the documented retention behavior. The worker uploads bounded case excerpts and reviewed-source text. Include this in the product disclosure. The service-only checkpoint holds candidate answers, evidence and opaque reasoning items until completion or terminal failure. Use access-controlled logs and never log these fields. Confirm retention settings, private case deletion behavior and any backup obligations before collecting real cases. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data#v1responses)

Submission intents precede the POST. A timeout or crash after provider acceptance may leave an unknown response ID. A signed webhook can reconcile it using provider metadata while the intent still exists. If reconciliation misses that window the run ends with an explicit unconfirmed status. The worker never resubmits an ambiguous POST. Cancellation immediately fences local publication. Provider cancellation is attempted for known responses and recent submissions with a recoverable receipt. Confirm cancellation limits on the hosted project.

To stop admission, set `NYAY_PAUSE_TURN_ADMISSION=true` for a controlled drain, or disable the resumable flag to halt both. Unschedule the sweep and webhook cleanup jobs after draining or cancelling outstanding work. Retain the migrations, chat events and results for inspection.
